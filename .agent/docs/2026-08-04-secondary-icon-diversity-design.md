# 新元素副图标多样性设计

## 目标

提高今后由模型动态生成元素的右下角副图标多样性，同时保留副图标的语义价值。
同一个元素必须稳定得到同一个图标配方，本地 FastAPI 与 Makers 运行时必须保持
一致。

本次不迁移、覆盖或重新计算已经持久化的图标。历史元素即使使用 `🧠`，也继续
沿用原配方。

## 当前问题

动态元素通常使用 `ai` 类别。现有规则只要在元素名、原料、类别、合成链或点评中
发现 `AI`、`智能`、`GPT`、`大模型` 或 `copilot`，就统一添加 `🧠` 副图标。
图标配方随后被写入 SQLite 或 KV，因此大量新元素会永久共享同一个副图标。

## 方案

采用“语义规则优先，稳定副图标池兜底”的两阶段解析。

第一阶段按元素名、两个原料及点评识别常见 AI 使用场景：

- 代码、开发和编程使用 `💻`；
- 文档、周报和写作使用 `📝`；
- 数据、分析和报表使用 `📊`；
- 聊天、对话和助手使用 `💬`；
- 图像、设计和视觉内容使用 `🎨`；
- 搜索、检索和知识使用 `🔍`；
- 自动化、工作流和智能体使用 `⚙️`。

这些规则作为现有 `keyword_badges` 的 `ai` 类别规则配置在
`backend/icon_rules.json` 中，并取代当前统一返回 `🧠` 的通用 AI 关键词规则。

第二阶段处理未命中具体语义的 `ai` 类元素。新增
`category_badge_pools.ai`，候选值为：

```text
🤖 ✨ 💡 🧠 🧩 ⚡
```

解析器使用规范化后的元素名称计算简单的跨语言稳定散列，再从候选池选择副图标。
选择前排除与主图标相同的候选，避免主副图标重复。候选池缺失、无效或过滤后为空
时不添加副图标。

## 解析顺序与兼容性

完整解析顺序保持为：

1. 使用有效的持久化图标；
2. 使用预置元素的审核图标；
3. 使用首条匹配的语义副图标规则；
4. 使用类别或合成链对应的稳定副图标池；
5. 回退为只有主图标和 palette 的配方。

持久化图标仍然拥有最高优先级，因此本次变化只影响尚未生成的新元素。已有元素
不会在读取、合成或启动加载时被改写。

图标规则生成器负责验证副图标池非空、成员不重复，并确认每个 Emoji 都存在于
已提交的 Emoji manifest。生成后的 Makers 数据继续由
`npm run generate:icon-data` 同步。

## 跨运行时一致性

Python 与 JavaScript 都先把元素名称规范化为 Unicode NFC，然后逐个 Unicode
码点计算 `hash = (hash * 31 + codepoint) % 2147483647`，最后以
`hash % 候选数` 选择副图标。稳定选择只以元素名称为身份键，不依赖原料顺序或
随机数，保证：

- 同名新元素重复解析时结果不变；
- `a + b` 与 `b + a` 不会造成图标跳动；
- FastAPI 和 Makers 返回相同配方。

## 测试与验证

共享 fixture 覆盖每个语义分组和至少一组未命中语义的兜底元素。Python 与
Makers 测试共同读取 fixture，验证：

1. 语义规则选择预期副图标；
2. 兜底选择稳定且在样本中产生多个不同副图标；
3. 副图标永远不与主图标相同；
4. 有效持久化配方继续胜出，历史 `🧠` 不会被替换；
5. 两个运行时解析结果一致；
6. 规则生成器拒绝无效、重复或 manifest 中不存在的池成员。

完成实现后运行项目要求的验证：

- `npm test`
- `python3 -m pytest tests --ignore=tests/test_combine_feedback.py -q`
- `npm run build`
