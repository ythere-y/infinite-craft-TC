# Local and Makers Runtime Parity Design

Date: 2026-08-03

## Objective

Make the FastAPI development backend and the EdgeOne Makers production
backend share one modular combination-prompt definition and align every
public API behavior that does not inherently depend on transactions,
strong consistency, long-lived connections, or a specific model provider.

The work must preserve local/production data isolation. Local development
must continue to use Redis, SQLite, and the locally configured model API;
Makers must continue to use its bound KV namespace and Makers Models.

## Success criteria

1. There is exactly one hand-edited source for the combination prompt,
   examples, style formulas, weights, and prompt section limits.
2. Given the same inputs, community examples, avoid words, bounty
   candidates, and deterministic random value, Python and JavaScript build
   byte-for-byte identical system and user messages.
3. Public community endpoints have matching routes, status behavior,
   pagination parameters, response fields, visibility rules, and ordering.
4. Makers feedback examples use the same qualification and ranking rules as
   the local SQLite implementation.
5. An authoritative seed formula cannot remain shadowed by a stale Makers
   formula or combination cache after that pair is next accessed.
6. Default Docker development and Makers use the same committed nickname
   corpus.
7. Cross-runtime contract tests fail when these behaviors drift again.

## Chosen approach

Use declarative shared JSON as the canonical source and generate only the
runtime-specific artifact that Edge Functions require.

This is preferred over treating Python or JavaScript source as canonical
because neither runtime should have to parse the other language. It is also
preferred over storing the base prompt in production KV because local code
must not connect to Makers KV and a runtime configuration layer would add
versioning, caching, and rollback concerns before they are needed.

## Shared prompt specification

Create `shared/combine-prompt.json` with this logical structure:

```json
{
  "schema_version": 1,
  "temperature": 0.85,
  "system_modules": [
    {
      "id": "identity",
      "enabled": true,
      "order": 10,
      "content": "..."
    }
  ],
  "examples": [
    {
      "id": "meeting-nesting",
      "enabled": true,
      "tags": ["invented-word", "same-input"],
      "input": {"a": "会议", "b": "会议"},
      "output": {
        "name": "会议套娃",
        "emoji": "🪆",
        "comment": "为了对齐上个会，再开一个会。"
      }
    }
  ],
  "styles": [
    {
      "id": "invented-word",
      "enabled": true,
      "label": "偏自造词",
      "guidance": "优先组合常见字，创造一看就懂的新词。",
      "weight": 0.3
    }
  ],
  "limits": {
    "avoid_words": 30,
    "community_examples": 8,
    "bounty_candidates": 12
  }
}
```

Stable IDs make each section independently controllable and prepare the
prompt for later formula promotion or experimentation. This change does not
automatically promote user-generated formulas into the base specification;
community feedback remains a separate runtime input.

The validator rejects:

- unsupported schema versions;
- duplicate or blank IDs;
- enabled style weights that are not positive or do not sum to 1;
- missing example fields;
- invalid or non-positive limits;
- an empty enabled system-prompt set.

`backend/prompt.py` reads the canonical JSON through a small Python loader.
The Docker image copies `shared/`, and Compose mounts it read-only so the
local runtime sees the same source as tests.

`scripts/generate-makers-prompt-data.mjs` validates the same JSON and writes
`edge-functions/_generated/prompt-data.js`. The committed generated module
contains data only and is regenerated by `npm run build`. Edge runtime code
never accesses the filesystem.

## Prompt rendering and model transport

Both renderers expose the same conceptual interface:

```text
build_prompt_messages(
  a,
  b,
  avoid_words,
  bounty_candidates,
  community_examples,
  deterministic_style_value
) -> {system, user, temperature, style_id}
```

Rendering rules are part of the contract:

1. Enabled system modules are sorted by `order`, then joined with one blank
   line.
2. Enabled fixed examples retain specification order.
3. Community examples, avoid words, and bounty candidates use the shared
   limits.
4. Weighted style selection uses half-open cumulative intervals. A random
   value equal to a boundary selects the following interval.
5. The selected style contributes both its label and its guidance.
6. Dynamic sections and the final input always appear in the same order.

The Python LLM transport gains an optional system message while retaining
the existing provider-neutral configuration and legacy single-question
call shape for callers outside combination generation. Combination
generation in both runtimes sends the same two messages and shared
temperature.

Provider, retry, reasoning, and content-safety settings remain
environment-specific. Therefore equal messages do not promise equal model
outputs.

## Community API parity

### Public listing

Both implementations support:

```text
GET /api/community/formulas?limit=<1..100>&offset=<non-negative>
```

Makers reads the complete 500-record public hot index, loads records in
bounded batches, filters non-public and takedown records, sorts by net score
descending and publication time descending, and only then applies offset
and limit. This removes the current error where Makers sorts only the first
100 index entries.

The 500-record Makers catalogue window remains an explicit capacity
boundary. Increasing it without an external transactional index would risk
the Edge Function CPU and KV-read budgets. Formula detail remains available
by ID even when an item ages out of this window.

### Formula detail

Add the Makers equivalent of:

```text
GET /api/community/formulas/{formula_id}
```

It returns 404 for missing, hidden, or takedown formulas; otherwise it
returns the same public fields, icon enrichment, net score, and current
player vote as FastAPI. FastAPI adopts the same takedown rule.

### Administrator logout

Add:

```text
POST /api/community/admin/logout
```

Makers expires `craft_admin` using the same path, HttpOnly, SameSite, and
Secure attributes as the login cookie. The response is `{"ok": true}`.

### Feedback examples

Makers positive examples:

- must be public and active;
- must treat a missing `ai_positive_enabled` field as enabled for backward
  compatibility;
- must exclude records where the field is false or zero;
- must satisfy the shared environment thresholds;
- must be sorted by net score descending, then updated time descending;
- must be limited to the shared prompt community-example count.

A bounded recent-retirement index records formula IDs when moderation or
seed reconciliation retires a formula. Negative results are loaded from
this index in retirement-time order. Existing retired records in the public
index remain a fallback during migration, so deployment does not erase the
current negative signal.

## Authoritative seed reconciliation

FastAPI keeps its eager startup reconciliation. Makers performs equivalent
lazy reconciliation because an Edge Function has no application-wide
startup phase and must not scan all formulas on every invocation.

For any accessed pair that exists in generated seed data:

1. The seed result is selected before a dynamic KV combination.
2. If the active community formula differs in result, emoji, comment, or
   source, the old formula is preserved as a retired hidden version.
3. A new hidden active version is created from the seed with the next
   version number.
4. The active pointer is moved to the seed version.
5. A conflicting combination cache is replaced by the authoritative seed
   representation without discarding its existing hit count.
6. Repeating the operation is idempotent and does not create another
   version.

These writes remain best effort under cross-edge concurrency. Deterministic
formula IDs and read-after-write verification prevent avoidable duplicate
versions, but the design does not claim SQL-strength transactions.

## Shared nickname corpus

Create a committed `shared/nickname-data.json` snapshot generated from the
filtered THUOCL sources. It contains the existing 7,831 chengyu and 4,350
state words.

The manual corpus-refresh script writes this JSON when the ignored THUOCL
checkout is available. Normal builds read the committed snapshot and
generate the Makers JavaScript module without requiring `words/`.
`backend/nickname.py` reads the same snapshot and retains its small fallback
only for damaged or incomplete installations.

This aligns candidate pools and weights. Random outputs and uniqueness
claims can still differ because each environment has an independent random
stream and datastore.

## Request-contract alignment

Application-level validation constants become shared documented values:

- combination inputs `a` and `b`: at most 80 Unicode code points;
- discoverer: at most 80 Unicode code points;
- session ID: at most 128 Unicode code points;
- recipe verification: at most 500 recipes;
- recipe `a`, `b`, and `result`: at most 80 Unicode code points.

FastAPI adds explicit checks matching the Makers error meaning. Makers keeps
its one-megabyte request-body enforcement because this is also a platform
limit. The local server does not need to emulate transport-level truncation
to achieve application-contract parity.

Production-only model rate limiting and dashboard authentication remain in
place. Local development may remain convenient under `APP_ENV=dev`; weaker
local security behavior is not copied into production.

## Explicitly retained runtime differences

The following are platform or deployment properties, not drift defects:

- Redis and SQLite can provide atomic operations and transactions; Makers
  KV is eventually consistent and cannot.
- Makers first and nickname claims remain best-effort under extreme
  cross-edge concurrency.
- Makers uses short polling for the wall while FastAPI retains an SSE
  compatibility endpoint.
- Makers management statistics remain approximate and capacity-bounded.
- Makers Models and the locally configured provider can return different
  outputs for identical messages.
- Local and production caches, first discoveries, votes, and player data
  remain completely isolated.

## Error handling and migration

- Invalid shared prompt or nickname data fails tests and the Makers build;
  it never silently deploys fallback prompt content.
- Existing formula records without `ai_positive_enabled` remain eligible.
- Existing public and retired indexes remain readable; new retirement
  records augment them.
- Existing generated prompt edits in `edge-functions/_lib/llm.js` are
  replaced by imports from the generated module, preserving their current
  content through the canonical JSON.
- No production KV migration job or local connection to Makers KV is
  required.

## Testing strategy

Implementation follows red-green-refactor for each behavior.

### Prompt tests

- schema validation failures;
- fixed style-weight boundary selection;
- exact Python/JavaScript system and user message parity for a shared
  fixture;
- generated Makers artifact is current;
- model requests use the shared temperature and two-message shape.

### Community tests

- sorting occurs before pagination across more than 100 formulas;
- detail returns current vote and rejects hidden/takedown formulas;
- logout clears the administrator cookie;
- positive feedback observes thresholds, ordering, and
  `ai_positive_enabled`;
- negative feedback uses recent retirement order;
- seed conflict creates exactly one new active version and preserves the
  retired version;
- repeated seed reconciliation is idempotent;
- stale combination KV cannot override a seed.

### Nickname and validation tests

- Python and JavaScript report identical corpus sizes and configured
  weights;
- Docker/build inputs include the shared snapshot;
- both APIs reject the same overlong application fields and oversized
  recipe batches.

### Required final verification

Run:

```text
npm test
python3 -m pytest tests --ignore=tests/test_combine_feedback.py -q
npm run build
```

A deployment maintainer with EdgeOne CLI also runs:

```text
npm run makers:build
```

## Rollout

The changes ship as one compatibility release because the generated prompt
artifact and its consumers must change together. No online data is deleted.
After deployment, existing formulas are reconciled only when their pair is
accessed, keeping edge request cost bounded.

Production smoke checks cover health, one seed combination, one cached
combination, community list/detail, and an authenticated administrator
login/logout. A model smoke call is optional because it consumes quota and
model output is nondeterministic; request construction is covered by
contract tests.
