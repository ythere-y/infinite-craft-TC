# 全局贴纸 Icon 系统设计

## 背景

当前游戏直接把后端 `emoji` 字符渲染为元素图标，操作按钮也大量使用原生
Emoji。预设库共有 591 个元素，但只使用 312 个不同 Emoji；421 个元素位于
重复图标组中，共有 142 个重复组。最高频的 `💼`、`🎮`、`🏢` 分别被 10、9、
6 个概念共用。

问题不只是重复：

- 原生 Emoji 随操作系统变化，游戏缺少稳定的自身风格；
- 元素、操作、状态都使用 Emoji，视觉语义混在一起；
- 类别、首发和基础元素没有统一的图形语法；
- 单纯根据词面拆分重复图标会产生实体消歧错误，例如把 `Riot` 按英文表面
  联想成闪电，而不是识别为“拳头游戏”；
- 侧栏的次级说明和较大图标降低首屏容量。

## 目标

- 建立全局统一且具有“鹅厂无限合成”辨识度的 Icon 系统。
- 元素使用彩色贴纸；操作使用同体系的双调界面图标。
- 在保证语义正确的前提下，显著减少元素图标重复。
- 通过两个图标组成一张贴纸，为品牌、人物、职位和长尾概念提供更多视觉签名。
- 侧栏只常驻“图标 + 名称”，三列密排，首屏可见约 24～30 个元素。
- 保持现有 Emoji、历史记录和 API 的向后兼容。
- 本地开发、Makers 生产和断网回退使用一致的本地素材，不依赖运行时 CDN。

## 不包含

- 不使用 Apple Emoji 图形；其素材不许可商业使用。
- 不使用授权不清晰的 Facebook Emoji 图形。
- 不为 591 个元素逐个绘制全新插画。
- 不在 Edge Function 中运行 embedding 模型。
- 不改变元素名称、配方结果、计分或发现语义。
- 不要求一次性人工设计所有动态生成元素。

## 已确认的视觉方向

### 1. 元素贴纸

Noto 图形作为贴纸主图，外层增加：

- 分类色背景；
- 白色描边；
- 轻微阴影和不超过 2° 的固定倾斜；
- 可选的小语义徽章；
- 最多一层状态装饰。

17 个业务类别归并为约 6 组色系，避免颜色过碎：

1. 原始与自然；
2. 鹅厂与产品；
3. 打工与办公；
4. 游戏与工作室；
5. 人物与社会；
6. 建筑、地理与抽象概念。

色系表达类别，不承担精确分类文字。完整类别放入悬停提示或详情。

### 2. 操作图标

顶部导航、搜索、清空、帮助、投票、公开、展开和关闭等操作统一使用
Phosphor Duotone SVG。操作图标放在冷色浅底容器内，与彩色元素贴纸共享圆角、
描边和阴影规则，但不会被误认成可合成元素。

只打包实际使用的 Phosphor SVG，不引入完整运行时依赖。

### 3. 紧凑尺寸

| 场景 | 图形尺寸 | 规则 |
| --- | ---: | --- |
| 侧栏 | 27px | 三列，只常驻名称 |
| 画布、拖拽影子、配方 | 30px | 保持足够命中区域 |
| 顶部操作 | 16px | 放在 25px 浅色容器中 |
| Toast、首发墙、详情 | 36～44px | 允许成为视觉焦点 |

类别、用途、来源等次级文字从列表移除。发现者、类别和来源通过 `title`、自定义
Tooltip 或详情弹窗展示。

### 4. 状态装饰

一张贴纸最多叠加一项状态，避免角标堆积：

- 基础元素：`原`角标；
- 全球首发：金色外圈和星光；
- 我的新发现：紫色外圈；
- 拖拽中：降低透明度；
- 合成目标：蓝色外圈；
- 加载失败：保留贴纸外壳并显示原生 Emoji 或 `❓`。

## 素材与授权

项目已经下载 `words/emoji-data/`。其中 Google/Noto 图形具有明确的 Apache
2.0 授权，当前预设使用的 312 个不同 Emoji 在 Google 素材中全部存在。

生产构建使用 `img-google-64`：

- 共约 3,786 个图形；
- 实际文件总大小约 13.7MB；
- 每个元素独立文件，浏览器只按需加载当前可见图标；
- 不使用会令首屏一次下载 5～14MB 的整张 spritesheet。

`words/emoji-data/` 只作为离线生成源，不成为 Makers CI 的隐式依赖。离线脚本
把允许发布的 64px 图形和 manifest 生成到
`frontend/assets/icons/generated/`，生成结果提交到仓库；常规生产构建只验证并
复制这些已固定版本的产物。这样 CI 不需要下载或携带本地 7.2GB 素材仓库。

操作图标使用 MIT 授权的 Phosphor Icons。构建产物继续保留并扩充
`THIRD_PARTY_NOTICES.md`，记录 Noto、Phosphor 和图标构建数据的来源及许可。

## 数据模型

### 1. 保留 `emoji`

`emoji` 继续是元素的语义兼容字段。旧缓存、旧配方、搜索和导入导出仍可读取
它。贴纸系统不要求修改现有 591 个元素和组合记录的 `emoji`。

### 2. Icon 配方

新增可选的 Icon 配方：

```json
{
  "base": "👊",
  "badge": "🎮",
  "palette": "studio",
  "source": "curated"
}
```

- `base`：Noto 主图，必填；
- `badge`：可选的第二个 Noto 图形，位于右下角；
- `palette`：视觉色系，而不是原始业务类别；
- `source`：`curated`、`entity`、`generated` 或 `fallback`。

完整视觉签名定义为：

```text
base + badge + palette
```

主图允许在语义相近的元素之间复用；完整视觉签名应尽量唯一。

### 3. 预设映射

新增生成产物 `element-icon-map.json`，以元素名为键保存 591 个预设元素的显式
配方。它独立于 `seed_elements.json`，避免为了视觉调整改动游戏的语义 Emoji。

示例：

```json
{
  "Riot": {
    "entity_type": "company",
    "canonical_name": "Riot Games",
    "aliases": ["拳头", "拳头游戏"],
    "icon": {
      "base": "👊",
      "badge": "🎮",
      "palette": "studio",
      "source": "curated"
    },
    "rationale": "腾讯投资的游戏工作室；中文通称拳头游戏"
  }
}
```

映射必须保存简短的 `rationale`，使人工复核和后续调整有依据。

### 4. 动态元素

动态元素继续由模型返回名称、Emoji 和点评。首次创建元素时，服务端生成并保存
一个可选 `icon` 配方：

1. 以模型 Emoji 为主图候选；
2. 根据名称、业务 chain、两个原料及点评确定实体类型和语义；
3. 如果主图已经高频使用，从预构建关键词索引选择更具体的 Noto 候选；
4. 找不到准确单图时，从原料或业务语义中选择一个徽章；
5. 配方随元素记录持久化，以后所有配方和页面复用同一个视觉签名。

本地 FastAPI 与 Makers Edge Function 读取同一份生成数据，并执行相同的确定性
规则。旧记录没有 `icon` 时在读取时生成兼容配方，不强制迁移历史数据。

API 只增加可选字段，不删除或重命名现有字段：

```json
{
  "name": "Riot",
  "emoji": "🎮",
  "icon": {
    "base": "👊",
    "badge": "🎮",
    "palette": "studio"
  }
}
```

## 实体感知映射

### 1. 优先级

映射选择必须遵循：

1. 语义正确；
2. 实体消歧；
3. 降低重复。

宁可暂时共享合理图标，也不能为了唯一而产生错误联想。

### 2. 命名实体知识层

品牌、产品、人物、职位、英文缩写和办公地点需要显式记录：

- `entity_type`；
- `canonical_name`；
- 中文名和常见别名；
- 业务类别和所属分组；
- 图标关键词；
- 禁止的错误词面解释；
- 已确认的 Icon 配方和理由。

例如：

- `Riot` → `Riot Games / 拳头游戏` → `👊 + 🎮`；
- `Epic` 在 `studio` 中 → `Epic Games` → `🛡️ + 🎮`；
- `COO` → 职位 / 运营 → `🧑‍💼 + ⚙️`；
- `任宇昕` → 人物 / 游戏业务 → `👔 + 🎮`。

### 3. 上下文消歧

自动候选不能只看元素名。它同时使用：

- `category`；
- 悬赏分组；
- 产生该元素的两个原料；
- chain；
- 合成点评；
- 已知别名。

`Epic` 在游戏工作室分组中必须按公司处理；只有普通抽象语境里的 “epic”
才允许按“史诗、宏大”理解。

### 4. 人工复核

人工复核优先级：

1. 所有品牌、人物和英文缩写；
2. 142 个重复组；
3. 首页、基础元素、悬赏和高频配方；
4. 低置信度自动候选；
5. 其余普通名词。

已有 `backend/emoji_pool.json` 可提供候选，但它当前只有英文短名和粗类别，不能
直接作为最终映射。构建阶段应加入中文别名和项目领域知识，不引入 Edge 端
embedding。

## 前端组件

### `ElementIcon`

唯一负责元素图标：

```text
ElementIcon(name, emoji, category, icon?, state?, size?)
```

解析顺序：

1. API 返回的持久化 `icon`；
2. `element-icon-map.json` 中的显式映射；
3. 基于 `emoji` 的单图配方；
4. 原生 Emoji 贴纸；
5. `❓` 贴纸。

它负责图像懒加载、异步解码、失败回退、色系、徽章和状态装饰。

### `ActionIcon`

唯一负责操作 SVG：

```text
ActionIcon(name, label, tone?, size?)
```

可见文字在桌面保留；窄屏允许折叠为纯图标，但必须提供 `aria-label` 和
Tooltip。

### 覆盖范围

`ElementIcon` 覆盖：

- 侧栏；
- 画布和拖拽影子；
- 配方库；
- 合成 Toast；
- KPI 历史中的元素；
- 首发墙；
- 悬赏图鉴；
- 配方详情和管理页。

`ActionIcon` 覆盖顶部导航、搜索、清空、帮助、打开/关闭、公开、投票、分页和
筛选操作。

## 兼容性

- 保留现有 `.emoji` 外层 DOM 类，内部从文本变成图片或组合贴纸。
- 老板黑话模式继续查找 `.emoji`，只替换贴纸内容并锁定尺寸，避免画布元素
  位移。
- 元素搜索仍使用名称和原始 Emoji 数据，不依赖图片文件名。
- 导入旧配方时没有 `icon` 也能正常显示。
- 图片加载失败不影响拖拽、合成、投票或公开操作。
- 画布上的视觉图标可以缩小，但元素命中区域不得小于当前可用尺寸。

## 构建流程

新增构建步骤：

1. 从 `words/emoji-data/emoji.json` 生成标准化 Unicode 序列映射；
2. 把 `img-google-64` 生成为
   `frontend/assets/icons/generated/emoji/` 中的固定版本资产；
3. 生成
   `frontend/assets/icons/generated/emoji-icon-manifest.json`；
4. 生成或验证
   `frontend/assets/icons/generated/element-icon-map.json`；
5. 复制允许使用的 Phosphor SVG 子集到
   `frontend/assets/icons/actions/`；
6. 生成授权清单；
7. 输出映射审计报告；
8. 在常规构建中验证上述提交产物与源数据版本一致。

Emoji 归一化必须支持：

- variation selector；
- ZWJ 序列；
- 肤色序列；
- keycap 和组合序列；
- 非限定与全限定形式。

## 错误处理与性能

- 图像使用 `loading="lazy"` 和异步解码；
- 只加载当前可见的独立 PNG，避免整张 spritesheet 阻塞首屏；
- 同一图形路径由浏览器缓存；
- 徽章加载失败时只隐藏徽章，不影响主图；
- 主图失败时回退原生 Emoji；
- 映射文件失败时回退现有裸 Emoji 行为；
- 不发起第三方网络请求；
- 映射生成失败应让构建失败，而不是部署半套系统。

## 验收标准

### 语义

- 所有品牌、人物、职位和英文缩写有显式映射及理由。
- `Riot` 固定为拳头语义，不能回归为闪电或暴乱类图形。
- `Epic` 在工作室语境中固定为游戏公司语义。
- `COO` 固定为职位/运营语义。
- 每个高频重复组经过人工复核。

### 重复率

- 语义正确优先于数字指标；
- 完整视觉签名重复率目标低于 10%；
- 同一完整视觉签名默认不超过 2 个元素；
- 允许语义合理的例外，但必须在映射中记录理由。

“完整视觉签名重复率”定义为：处在重复
`base + badge + palette` 组中的元素数除以全部已映射元素数。审计报告同时输出
主图重复率，避免用大量无意义徽章掩盖主图仍然单调的问题。

### UI

- 侧栏三列、只常驻名称；
- 常规桌面首屏显示约 24～30 个元素；
- 画布拖拽命中区域不因图形缩小而退化；
- 元素和操作图标不会互相误认；
- 老板模式切换前后画布元素的位置和尺寸稳定；
- 主游戏、配方库、Toast、首发墙和移动端视觉一致。

### 自动化测试

- 591 个预设元素都有合法 Icon 配方；
- 当前 312 个 Emoji 均有 Noto 图形；
- 复合 Emoji 和 ZWJ 序列解析正确；
- 所有配方引用的主图和徽章文件存在；
- 实体语义回归集包含 `Riot`、`Epic`、`COO` 等已确认案例；
- 映射审计报告计算主图重复和完整签名重复；
- 图片失败时回退不影响元素名称和交互；
- 页面不再直接使用裸 Emoji 作为操作图标；
- 窄屏纯图标按钮具有可访问名称。

## 实施顺序

1. 建立素材构建脚本、授权清单和 Unicode manifest；
2. 建立 `ElementIcon`、`ActionIcon` 和尺寸/色系 token；
3. 替换主游戏和操作按钮；
4. 替换配方库、Toast、KPI、首发墙和管理页；
5. 建立 591 个预设元素的候选映射与审计报告；
6. 人工复核命名实体和高频重复组；
7. 加入双图组合和动态元素持久化；
8. 完成老板模式、失败回退、性能和移动端验收。

## 已考虑但不采用

### 直接使用原生 Emoji

实现最简单，但跨平台不一致，无法形成品牌风格，也无法解决重复。

### 全面使用 Fluent 3D

质感强、许可友好，但需要新增完整素材管线，且 3D 图形本身不能解决实体消歧。

### 混合 Game-icons / Iconify 作为元素主图

长尾覆盖丰富，但会让元素主图出现明显不同的绘画语言。免费图标库可作为候选
研究来源，不直接混入 Noto 贴纸主图。

### 只做自动词面匹配

能快速降低重复数字，但会把品牌、人物和英文缩写误解成普通词。实体知识层和
人工复核是上线前的硬门槛。
