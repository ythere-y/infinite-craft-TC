# 分数与 QQ 星级系统改造设计

## 背景与目标

当前产品把累计成长值称为“KPI”，首页直接展示具体分数，并使用传统绩效档位、
瑞雪及有限星级混合表示等级。新版本将累计值统一称为“分数”，并完全使用 QQ
式四进制等级：

- 4 颗星星合成 1 个月亮；
- 4 个月亮合成 1 个太阳；
- 4 个太阳合成 1 个皇冠；
- 等级展示最多计算 65,535 个等价星（其中最多 1,023 个皇冠），避免异常高分
  生成过长图标串。

分数仍是唯一持久化事实，星级只是由累计分数实时推导出的展示。现有玩家的分数
不重置、不迁移，升级后直接按新规则换算等级。

### 初始星星

所有玩家无条件获得一颗不占分数的基础星。累计分数和加分历史仍从零开始，不为
基础星创建虚构的加分记录。

```text
display_units = min(MAX_LEVEL_UNITS, earned_units(score) + 1)
```

其中 `earned_units(score)` 仍由原分数阈值公式计算。关键映射为：

| 累计分数 | 展示等级 |
| ---: | --- |
| 0 | 🌟 |
| 300 | 🌟🌟 |
| 620 | 🌟🌟🌟 |
| 960 | 🌙 |
| 1,320 | 🌙🌟 |

等级进度继续表示距离下一颗“分数星”的区间比例。升级与融合动画比较加分前后的
`display_units`，因此 300 分会生成第二颗星，960 分会把四颗星融合为月亮。

## 范围

本次改造覆盖：

- Python 本地后端和 EdgeOne 生产后端的等级计算；
- 首页等级按钮及响应式布局；
- 分数记录面板、加分历史和等级进度；
- 合成后的加分反馈；
- 获得星星以及星、月、太阳四合一时的顶栏动画；
- API、前端状态、文档和测试中属于分数功能的用户可见“KPI”文案。

不删除游戏内容中的“KPI”元素、相关配方或昵称词库。它们是合成玩法内容，
不是分数功能名称。

## 分数与等级模型

### 真实数据

累计分数是唯一真实数据。现有浏览器本地存储 `ic_kpi` 和既有
`/api/.../kpi` 路由暂时保留，确保已有玩家数据和旧客户端仍然可用。新增内部
变量、函数和用户可见文案使用 `score`、`分数`、`level`、`等级` 命名。

### 逐星递增曲线

第 `n` 颗等价星所需的新增分数为：

```text
cost(n) = 300 + 20 × (n - 1), n >= 1
```

获得前 `n` 颗等价星所需的累计分数为：

```text
threshold(n) = 10n² + 290n
```

选择这组参数有两个目的：

1. 第二颗展示星在正常手动合成若干次后即可获得；
2. 因基础星参与四进制融合，第一顶皇冠的累计门槛为 57,960，与旧系统
   59,200 的皇冠门槛接近，
   避免现有高分玩家升级后发生明显的等级跃迁。

阈值属于内部规则，不出现在玩家界面。等级计算通过整数二分查找或等价的稳定
整数算法求出满足 `threshold(n) <= score` 的最大 `n`，避免浮点边界误差，
在等级展示上限内稳定计算。

### 分数累计与等级展示上限

累计分数和等级展示是两个独立概念：

- 累计分数继续增长并持久化，不因等级达到上限而截断；
- 加分历史始终记录真实的本次加分和累计结果；
- 等级计算最多使用 65,535 个等价星，对应最多 1,023 个皇冠；
- 达到上限后，首页和面板的等级图标固定，不再计算新的星级边界；
- 上限后的普通 `+N 分` 飞入与残留反馈继续播放；
- 上限后不再生成星星、不执行四合一融合，也不播放升级特效。

该上限只限制前端等级展示和升级动画，不限制玩家继续获得分数。

### 四进制拆分

包含基础星的展示等价星数 `n` 按以下权重从高到低拆分：

| 图标 | 等价星数 |
| --- | ---: |
| 👑 | 64 |
| 🌞 | 16 |
| 🌙 | 4 |
| 🌟 | 1 |

展示顺序固定为皇冠、太阳、月亮、星星。在展示上限内，皇冠数量不取模，其余
单位分别落在 `0..3`。零分时直接显示基础星，不显示“尚未获得星星”占位状态。

等级计算结果提供：

- 包含基础星在内的展示等价星数；
- 皇冠、太阳、月亮和星星数量；
- 当前完整图标串；
- 当前星级区间的无数字进度比例；
- 是否刚跨越一个或多个星级边界。

不再提供传统绩效档位、瑞雪段位、封顶状态或有限段位列表。

## 首页等级按钮

首页原“KPI + 数字”按钮改为“等级 + QQ 图标串”，不展示累计分数。

按钮优先完整展示真实图标串，不使用数量角标或文字摘要。为适应较长皇冠串：

- 顶栏使用弹性布局，等级按钮可收缩但不能挤坏花名和其他操作；
- 等级内容设置响应式最大宽度；
- 超出可用宽度的右侧内容使用渐隐裁切，不出现生硬省略号；
- 移动端使用更小的最大宽度，仍从最高等级图标开始展示；
- 点击按钮打开面板后可查看不裁切的完整等级；
- `title` 和无障碍文本包含完整的文字等级描述。

## 分数记录面板

原“KPI 复盘”统一改名为“分数记录”。

面板保留并展示：

- 具体累计分数；
- 当前完整等级图标串；
- 原有逐条加分历史和每次增加的具体分数；
- 当前星级区间内的无数字进度条；
- “4 星 = 1 月、4 月 = 1 日、4 日 = 1 冠”的规则说明。

面板不展示：

- 距离升级还差多少分；
- 下一等级的具体阈值；
- 有限的段位路径列表；
- 旧绩效、瑞雪或封顶文案。

## 加分与升级反馈

### 普通加分

每次手动合成后，`+分数` 从合成结果飞向首页等级按钮。动画比现有版本稍慢，
抵达后在按钮附近保持清晰可读，再渐隐消失。未跨越星级边界时，按钮播放一次
轻量的吸收闪光。

### 获得新星

跨越星级边界时，所有生成与融合过程都限制在等级按钮内部，不遮挡画布：

1. 新获得的星星在按钮内生成；
2. 星星并入当前图标串；
3. 若形成四颗同级图标，四个图标聚拢并闪光；
4. 四个图标被一个高一级图标替换；
5. 连锁合成按星星、月亮、太阳、皇冠顺序继续。

一次加分跨越多个星级边界时，事件进入串行动画队列。第一段完整播放，后续段落
适度加速，并设置总时长上限；动画完成后必须与累计分数计算出的最终等级一致。
新的手动合成可以继续进行，不锁定画布。

若加分前已经达到等级展示上限，或本次加分到达上限后仍有溢出分数，则只保留
普通加分飞入与残留反馈。等级计算在上限处停止，不为溢出分数创建星星、融合
步骤或升级动画。

页面切换、节点销毁或动画异常时，队列直接结束并渲染最终等级，不能让展示状态
滞后。系统启用 `prefers-reduced-motion: reduce` 时，不播放飞行、生成和融合，
只显示延长停留的加分文字、一次按钮高亮以及最终等级。

## 后端与前端职责

Python 和 EdgeOne 后端各自实现同一套纯等级计算函数，并保持返回结构一致。
前端使用相同规则计算加分前后的星级边界，以即时启动动画；接口返回用于面板
渲染和兼容校验。

既有加分规则、分数历史和合成得分逻辑不在本次范围内改变。只调整累计分数到
等级的换算以及展示方式。

旧接口和字段继续接受请求，但：

- 新响应增加新的等级结构；
- 旧段位字段在兼容期内可保留为派生别名，前端不再使用；
- `/api/tiers` 改为返回等级规则或由新的等级规则接口替代，同时保留旧路由，
  避免旧页面报错；
- 所有新代码不继续扩散 `kpi` 命名。

## 错误处理

- 非数字、负数和缺失分数按零分处理；
- 累计分数限制在 JavaScript 安全整数范围内，等级展示单独限制为 65,535 个
  等价星；
- 等级规则接口失败时，前端使用同版本内置规则，不影响游戏；
- 本地缓存中的旧分数和历史格式继续可读；
- 动画失败不能影响分数写入、历史记录或最终等级渲染。

## 验证

### 领域测试

Python 与 EdgeOne 测试共同覆盖：

- 零分基础星、300 分第二颗星和 960 分首次融合为月亮；
- 初始基础星不改变总分或历史；
- 每颗星成本严格递增；
- 4 星合月、4 月合日、4 日合冠；
- 第一顶皇冠门槛与设计参数一致；
- 65 等价星和多个皇冠；
- 达到等级展示上限以及超过上限后继续累计分数；
- 每个阈值前一分、阈值本身和阈值后一分；
- 两套实现对同一组输入返回完全一致的拆分与进度。

### 前端测试

前端测试覆盖：

- 首页不出现累计分数，只出现等级；
- 面板显示累计分数和原有加分历史；
- 页面不再出现分数功能相关的“KPI”、绩效或瑞雪文案；
- 不显示“还差多少分”和具体等级阈值；
- 长图标串在桌面端和移动端保持顶栏布局稳定；
- 单次加分提示使用文本节点，不产生 HTML 注入；
- 新星生成、四合一、连锁合成和多次事件排队；
- 达到等级上限后仍累计分数和历史，只保留普通加分反馈；
- 动画中断后立即落到正确最终等级；
- 减少动态效果模式正确退化。

## 验收标准

1. 所有人从零分开始拥有一颗基础星，且不新增虚构的分数或历史记录。
2. 首页只显示自适应的 QQ 式等级图标，不显示具体分数。
3. 点击等级按钮后能查看总分、完整等级、无数字进度和原有加分历史。
4. 星、月、太阳、皇冠在 65,535 个等价星的展示上限内严格按四进制融合；
   达到上限后等级固定，但分数和历史继续累计。
5. 每颗星所需新增分数线性递增，阈值不向玩家展示。
6. 普通加分清晰可读；升级生成与融合只发生在顶栏等级按钮内。
7. Python、本地前端和 EdgeOne 生产实现保持一致，完整测试与构建通过。
