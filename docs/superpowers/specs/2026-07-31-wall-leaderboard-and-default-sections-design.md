# 首发墙排行榜与栏目默认状态设计

## 背景

首发墙当前包含“悬赏清单”“震撼首发”和右侧“打工人排行榜”。
现有排行榜按玩家的首发数量排序，但每行末尾只显示“76 个”一类缺少
名词的数值，用户无法快速理解其含义。榜单也是统一的单行列表，前三名
与其他名次缺乏视觉区分，整体显得僵硬。

本次改进同时调整两个栏目的首次进入状态，并重构排行榜的信息层级和
视觉表现。排行榜继续以首发数量为唯一排序依据，不切换为分数榜。

## 目标

1. 首次进入首发墙时，“悬赏清单”默认折叠，“震撼首发”默认展开。
2. 用户手动改变栏目状态后，继续记住用户选择。
3. 让榜单中的排序指标明确显示为“`N 个首发`”。
4. 使用领奖台突出前三名，第 4–20 名保持紧凑易扫。
5. 根据首发数量展示独立的“首发等级”，增强成长感。
6. 保持桌面端和窄屏可用，不引入横向滚动。

## 非目标

- 不改变排行榜的排序依据。
- 不改动排行榜 API、首发记录或后端存储结构。
- 不把主页分数迁移到排行榜。
- 不复用或修改主页的分数等级规则。
- 不调整首发墙的分页、搜索、轮询、悬赏内容或配方弹窗。

## 栏目默认状态

栏目继续使用现有的独立 `localStorage` 键保存折叠状态，但首次访问时
使用不同的默认值：

- “悬赏清单”：无已保存状态时折叠。
- “震撼首发”：无已保存状态时展开。
- 如果对应栏目已有保存值，则保存值优先于默认值。

按钮的 `aria-expanded`、箭头方向和正文可见性必须与初始状态一致。
异步内容加载后不能意外改变用户已经选择的折叠状态。

## 排行榜信息架构

### 标题与当前鹅

标题保留“打工人排行榜 · Top 20”。

“当前鹅”卡片始终显示，并包含：

- 当前昵称；
- 当前名次，未上榜时显示未上榜提示；
- 明确标注的首发数量；
- 首发等级图标和文字说明。

尚未获得首发的玩家显示“尚未获得首发星星”，不赠送初始等级。

### 前三名领奖台

前三名使用三列领奖台，视觉顺序为：

1. 左侧第二名；
2. 中间第一名；
3. 右侧第三名。

第一名卡片位置更高，并使用更明显的金色背景或边框。每张卡片包含：

- 奖牌；
- 昵称；
- `N 个首发`；
- 首发等级图标。

长昵称使用单行省略，`title` 提供完整昵称。

DOM 顺序保持第一名、第二名、第三名，使用 CSS 布局得到第二、第一、
第三的视觉顺序，保证辅助技术按真实名次阅读。

### 第 4–20 名

第 4–20 名使用紧凑双行列表：

- 第一行：名次、昵称、`N 个首发`；
- 第二行：首发等级图标。

当前玩家如果出现在榜单中，沿用现有高亮语义。榜单区域独立滚动，
避免页面其他区域跟随滚动。

## 首发等级规则

首发等级是只服务于首发排行榜的荣誉体系，与主页分数等级完全独立。
它不使用分数阈值，也不调用主页的 `SCORE_LEVEL.rankFor`。

每次首发对应一个等级单位：

- `1 次首发 = 1 🌟`；
- `4 🌟 = 1 🌙`；
- `4 🌙 = 1 🌞`；
- `4 🌞 = 1 👑`。

换算从最高级图标开始，使用四进制分解：

```text
crowns = floor(firsts / 64)
remainder %= 64
suns = floor(remainder / 16)
remainder %= 16
moons = floor(remainder / 4)
stars = remainder % 4
```

示例：

- `1 个首发 = 🌟`
- `4 个首发 = 🌙`
- `16 个首发 = 🌞`
- `64 个首发 = 👑`
- `76 个首发 = 👑 🌙 🌙 🌙`

视觉标签统一写作“首发等级”。无障碍名称和 tooltip 明确写作
“首发星星”或“首发荣誉等级”，避免与主页分数等级混淆。

## 图标布局与聚合

普通等级图标使用固定网格：

- 每行最多 5 个图标；
- 可自然扩展到最多 4 行；
- 最多直接展示 20 个图标。

如果四进制分解后的图标数量超过 20，不继续增加榜单行高。此时所有
非零等级都改用“图标 × 数量”聚合，例如 `👑 × 23`。皇冠、太阳、
月亮、星星各自最多生成一个聚合项，因此最多显示四个聚合项。

无论图标是否聚合，`N 个首发`始终单独显示，作为排序依据和精确数值。

## 数据流与实现边界

现有 `/api/wall/leaderboard` 返回的数据已经包含实现所需的
`rank`、`discoverer` 和 `firsts`。前端在渲染前根据 `firsts` 计算
首发等级，不新增 API 字段。

换算封装为无副作用的前端函数，例如：

```text
firstHonorFor(firsts) -> {
  crowns,
  suns,
  moons,
  stars,
  icons,
  ariaLabel
}
```

该函数只接受标准化后的非负整数。无效、负数或非有限值按 `0` 处理。
渲染层负责把返回结构转换为普通图标网格或聚合显示。

排行榜仍按后端返回顺序渲染。现有后端排序规则保持不变：首发数量降序，
数量相同时按昵称升序。

## 加载、空状态与错误状态

- 加载时继续显示现有“加载中”状态。
- 空榜时继续提示用户完成第一个首发。
- 请求失败时继续显示明确的加载失败信息。
- 单条数据缺少昵称时使用现有匿名名称策略。
- 无效首发数量显示为 `0 个首发`和“尚未获得首发星星”，不能导致整榜
  渲染失败。

## 响应式设计

桌面端维持现有右侧栏宽度和整体页面结构。

窄屏下：

- 排行榜继续位于首发内容下方；
- 三列领奖台保留，但缩小间距、内边距和字号；
- 昵称单行省略；
- 等级图标在各自卡片内按规则换行；
- 不产生横向滚动；
- 排行榜区域保持可滚动，用户仍能访问第 4–20 名。

如果最窄支持宽度下无法容纳完整的文字等级说明，优先保留图标、
`N 个首发`和无障碍名称，隐藏重复的视觉说明文字。

## 无障碍

- 折叠按钮的 `aria-expanded` 必须准确反映状态。
- 领奖台和列表仍按真实名次提供可理解的 DOM 阅读顺序，不能只依赖
  视觉位置表达名次。
- 等级图标容器提供完整 `aria-label`，单个装饰 icon 对辅助技术隐藏。
- 聚合显示的视觉文本和无障碍名称表达同一数量。
- 颜色不是区分当前鹅、第一名或等级的唯一方式。

## 测试策略

### 单元测试

覆盖首发等级换算：

- `0`：无图标；
- `1`：一颗首发星星；
- `4`：一个月亮；
- `16`：一个太阳；
- `64`：一个皇冠；
- `76`：一个皇冠、三个月亮；
- 无效、负数和非有限输入；
- 图标数量恰好为 20；
- 图标数量超过 20 后启用聚合。

### 前端结构与交互测试

- 无保存值时悬赏清单折叠、震撼首发展开；
- 有保存值时两个栏目分别恢复用户选择；
- 当前鹅卡片包含名次、首发数量和首发等级；
- 前三名按第二、第一、第三的视觉顺序渲染；
- 第 4–20 名使用紧凑列表；
- `N 个首发`包含明确单位；
- 当前鹅高亮、空榜和错误状态不回退。

### 响应式验证

在桌面和窄屏视口验证：

- 无横向溢出；
- 领奖台三张卡片均可见；
- 长昵称不会撑破卡片；
- 四行图标不会遮挡下一名；
- 榜单滚动可访问全部二十名。

## 验收标准

1. 首次访问时悬赏清单折叠、震撼首发展开。
2. 用户改变状态并刷新后，两个栏目分别恢复保存状态。
3. 所有榜单数字明确显示为“`N 个首发`”。
4. 前三名显示为第二、第一、第三的领奖台，第一名居中突出。
5. 第 4–20 名显示为紧凑双行列表。
6. 首发等级严格按首发数量和四进制规则计算。
7. 首发等级在文案、代码和无障碍语义上均与主页分数等级分离。
8. 图标每行不超过 5 个、最多 4 行，超量时聚合。
9. 排行榜 API 和后端排序逻辑没有变化。
10. 桌面端和窄屏均无横向溢出，所有榜单内容可访问。
